## Hard Constraints

### Universal (apply to every project using this harness)

1. **Harness first.** Keep `harness/feature_list.json` and
   `harness/progress.md` up to date with every scope or state
   change, as the work happens. No session state may live only in
   the conversation.
2. **Clean exit.** Before ending a session, complete every item in
   `harness/clean-state-checklist.md`. Features that reached
   `passing` move to `harness/feature_archive.json` in the same
   session's close-out.
3. **Commit messages** are a single short summary line (target 50
   characters): no body, no bullet list, no trailer, no
   conventional-commit type tag. A commit tied to a shipped build
   may be prefixed `[<Platform> v<version> b<build>]`.
4. **Linear history.** Never `git merge` to reconcile branches (no
   merge commits). Rebase or cherry-pick instead. PRs land with
   rebase-merge (`gh pr merge --rebase`). Force-pushing needs the
   user's explicit go-ahead every time; one approval never carries
   over to the next push.
5. **Never merge PRs, and never touch the mainline or an epic base
   branch directly**, unless the user asks for that specific action.
   Never propose landing an epic on the mainline; the user decides
   when.
6. **No installs without asking.** Never install packages, tools or
   dependencies on the host (`pip`, `npm`, `brew`, `gem`, Unity
   packages, ...) without explicit confirmation, including one-off
   installs for inspection.
7. **Check git before committing.** Run `git status` and
   `git log --oneline -3` right before any commit or branch
   operation; the user may commit between turns.
8. **Review iterations wait for approval.** On an open PR under
   review, make and verify the change, show it, and commit/push only
   after the user's explicit OK.
9. **Findings are discussions, not work orders.** When the user
   reports a warning, bug or observation without saying "fix it",
   investigate and present findings and options; write code only
   once they choose.
10. **No dead code.** Build only what is called: no speculative
    overloads, fields, helpers or flags. Unify incidental duplicates
    instead of keeping near-copies.
11. **Never edit `Library/`, `Temp/`, `Logs/`, `obj/` or
    `UserSettings/`.** They are git-ignored and regenerated by Unity.
12. **`.meta` files** are committed alongside every asset they
    describe, with stable GUIDs.
13. **Project assets stay under `{{PROJECT_ASSET_ROOT}}`** (and
    `Assets/Resources/` when loaded by path). Never move or create
    project content inside Unity/package-scaffolded folders.
14. **Verify through the Unity CLI**, not by assumption: compile,
    tests, Play mode and captures per `harness/docs/UNITY_CLI.md`.
    A feature is `passing` only when its `verification` field holds.
15. **Experiments are disposable.** Try risky or exploratory changes
    on a local branch, record the numbers, revert, and return to the
    branch you started from. Only the agreed result becomes a PR.

## How to Verify

```bash
# Compile, then run EditMode tests, against the open Editor
harness/scripts/unity-check.sh

# Or step by step (see harness/docs/UNITY_CLI.md)
unity cmd recompile --result-only
unity cmd recompile_status --result-only
unity cmd run_tests --mode EditMode
```

Tests live in `{{TEST_FOLDER}}`. They must pass before any feature
is marked `passing`. Look-and-feel changes are verified in Play mode
with captures, per each feature's `verification` field.

## Harness

- `harness/docs/UNITY_CLI.md`: driving the open Editor (compile,
  tests, Play mode, captures, live C# eval)
- `harness/docs/ARCHITECTURE.md`: scenes, asset layout, key classes
- `harness/docs/CODE_STYLE.md`: comments, naming, formatting
- `harness/docs/LOOP.md`: the feature loop and its review gate
- `harness/docs/STACKED_PRS.md`: epics as stacked branches and PRs
- `harness/feature_list.json`: current work only, schema in
  `harness/docs/FEATURES.md`
- `harness/feature_archive.json`: finished or dropped work, same
  schema; verification commands stay usable as regression checks
- `harness/progress.md`: session continuity log; read it first,
  update it before ending
- `harness/clean-state-checklist.md`: exit checklist for every
  session
- `harness/plans/`: phased plans for multi-PR work
- `harness/loop-state.md`: one-line checkpoint for the loop
- `docs/SDLC.md`: how the user and the agent work, from intent to
  documentation
- `docs/SUBAGENTS.md`: subagents and skills worth adding over time
